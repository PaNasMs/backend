# OstojaOS backend

Отдельный репозиторий серверной платформы.
Начальный рабочий прототип реализован.

Стек: Go, net/http + chi, coder/websocket, SQLite WAL, database/sql + sqlc,
PAM через libpam/cgo, Linux/systemd. Целевая архитектура ARM64.

## Границы

- Core — непривилегированный модульный монолит: API, сессии, настройки,
  задачи, события и бизнес-операции.
- Агент — отдельный привилегированный процесс с ограниченным локальным
  протоколом, проверкой отправителя/полномочий и конкретными операциями.
- Длительные и требующие изоляции задачи — рабочие процессы под systemd.
- Linux и службы остаются источником фактического состояния; перезапуск
  панели не останавливает Samba/NFS и RAID.
- Модули пользователей, хранилища и последующих функций входят в один
  репозиторий; HTTP-обработчики отделены от прикладной логики и Linux-адаптеров.
- Отдельный модуль терминала запускает PTY под пользователем и использует
  отдельный авторизованный WebSocket; терминальный поток не сохраняется
  в событиях core. Агент не превращается в shell-прокси для других модулей.
- Службы, журналы, обновления, история метрик, LUKS и внешние NFS/SMB-монтирования
  имеют отдельные адаптеры/сценарии. Сеть — последующий отдельный модуль;
  брандмауэр, LVM и диагностические архивы отложены.

## Структура при начале реализации

- `cmd/` — точки входа core, агента и необходимых рабочих процессов.
- `internal/` — общее ядро, функциональные модули и системные адаптеры.
- `api/` — исходный OpenAPI, схемы событий и версии контрактов.
- `migrations/` — миграции SQLite.
- `packaging/` — systemd units, Debian-поставка и установка/обновление.

Каталоги cmd, internal, api, packaging и Go-модуль созданы. Контракты
принадлежат backend; для frontend публикуется версионированный артефакт,
без обязательного отдельного репозитория контрактов. Формат выпуска
артефакта уточнить при настройке сборки.

Сборка backend не требует исходников frontend. Статические ассеты можно
поставлять готовым артефактом согласованной версии; конкретную сборку
дистрибутива определить при реализации поставки.

Первый поставляемый прототип обязан иметь независимый от UI/core/SQLite
путь remove/purge через SSH, реестр файлов и системных изменений и проверку
переустановки. Удаление панели сохраняет данные и системных пользователей;
для конфигурации внешних служб и охлаждения требуется безопасная передача
управления или восстановление без перезаписи чужих изменений.

и [задачи](../docs/implementation-tasks.md).

Текущий объём, сборка, проверки и удаление: [руководство прототипа](../docs/prototype-development.md).
